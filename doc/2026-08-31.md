## 1. Session vs JWT 비교

| 구분 | Session 방식 | JWT 방식 |
|------|------------|---------|
| 인증 정보 저장 위치 | 서버 메모리 (Session) | 클라이언트 (Cookie / Header) |
| 서버 상태 | Stateful (서버가 상태 보유) | Stateless (서버가 상태 미보유) |
| 서버 종료 시 | 로그인 정보 소멸 | JWT 유효 기간까지 유지 |
| 확장성 | 서버 증가 시 세션 공유 필요 | 토큰 자체 검증으로 확장 용이 |
| 요청 방식 | JSESSIONID 쿠키 자동 전송 | `Authorization: Bearer JWT` 헤더 |

**Session 방식 흐름**
```
로그인 → ID/PW 확인 → Session 생성 → JSESSIONID 쿠키 저장
→ 다음 요청 시 Session 확인 → 사용자 식별
```

**JWT 방식 흐름**
```
로그인 → ID/PW 확인 → JWT 생성 → 클라이언트에 저장 (Cookie)
→ 다음 요청 시 JWT 전송 → 서버에서 검증 → 사용자 식별
```

## 2. JWT 구조

```
xxxxx . yyyyy . zzzzz
  │       │       │
Header  Payload  Signature
         │
    실제 정보 저장
    (username, role, 만료시간)
```

| 구성 | 내용 |
|------|------|
| **Header** | 토큰 타입(JWT), 암호화 알고리즘 |
| **Payload** | 실제 데이터 (사용자 ID, 권한, 만료시간) |
| **Signature** | Header + Payload를 비밀키로 서명 → 위조 방지 |

> Payload는 Base64로 인코딩되어 있어 **복호화 가능**하므로 비밀번호 등 민감 정보는 담지 않는다.

## 4. 의존성 설정

```gradle
// build.gradle - JWT 라이브러리
implementation 'io.jsonwebtoken:jjwt-api:0.11.5'
runtimeOnly   'io.jsonwebtoken:jjwt-impl:0.11.5'
runtimeOnly   'io.jsonwebtoken:jjwt-jackson:0.11.5'
```

| 라이브러리 | 역할 |
|-----------|------|
| `jjwt-api` | JWT 생성·파싱 인터페이스 (컴파일 시 사용) |
| `jjwt-impl` | 실제 구현체 (런타임 시 사용) |
| `jjwt-jackson` | JSON 직렬화 처리 (런타임 시 사용) |

## 5. 클래스별 역할

| 클래스 | 역할 |
|--------|------|
| `AuthController` | 로그인 요청 수신 → `AuthenticationManager`에 인증 위임 → JWT 발급 후 Cookie 저장 |
| `JwtAuthenticationProvider` | JWT 토큰 생성(`createToken`) / 위조 검증(`validate`) / 사용자 ID·권한 추출 |
| `JwtAuthenticationFilter` | 모든 요청마다 Cookie에서 JWT 추출 → 검증 → `SecurityContextHolder`에 인증 정보 저장 |
| `JwtSecurityConfig` | URL별 접근 권한 설정 (일반 Security Config와 동일한 역할) |
| `CustomUserDetailsService` | DB에서 사용자 조회 → `UserDetails` 반환 |

**역할 한 줄 요약**
```
UserDetailsService  : 사용자 정보 저장 (DB 조회)
JwtAuthProvider     : 토큰 생성 및 검증
JwtAuthFilter       : 요청마다 토큰 종합 검사
JwtSecurityConfig   : URL 접근 권한 규칙 설정
Controller          : 실제 사용자 요청 처리
```

## 6. 전체 동작 흐름

### 1) 로그인 - JWT 발급

```
POST /member/login (id, pwd 전송)
        │
        ▼
AuthController
        │  AuthenticationManager.authenticate() 호출
        ▼
CustomUserDetailsService
        │  DB에서 사용자 조회 → 비밀번호·아이디 일치 확인
        ▼
UserDetails 반환 → 인증 성공
        │
        ▼
JwtAuthenticationProvider.createToken()
        │  사용자 id + 권한 + 만료시간 → JWT 생성
        ▼
JWT → Cookie에 저장 (accessToken)
        │
        ▼
/home 으로 redirect
```

### 2) 이후 요청 - JWT 검증

```
브라우저 요청 (Cookie에 JWT 자동 포함)
        │
        ▼
JwtAuthenticationFilter (OncePerRequestFilter)
        │  ① Cookie에서 accessToken 추출
        │  ② JWT 서명 검증 (위조 여부)
        │  ③ Payload에서 username 추출
        │  ④ CustomUserDetailsService로 DB 조회
        │  ⑤ SecurityContextHolder에 인증 정보 저장
        ▼
Controller 접근 완료
```

## 7. JwtAuthenticationFilter 처리 순서

`OncePerRequestFilter`를 상속받아 **요청당 한 번만** 실행된다.

```
① Header 확인 (Front에서 Authorization 헤더 전송 시)
② Cookie 확인 (accessToken 쿠키 추출)
③ JWT 검증 (서명 유효성, 만료 여부)
④ DB에서 사용자 조회 (UserDetailsService)
⑤ Security 인증 객체 생성 (UsernamePasswordAuthenticationToken)
⑥ SecurityContext에 저장
⑦ 다음 Filter / Controller 실행
```

> `OncePerRequestFilter` : 동일 요청에서 필터가 중복 실행되는 것을 방지  
> JWT 검증 실패 시 → SecurityContext에 저장하지 않음 → 권한 없음(403) 처리

## 💡 Note

### 오늘 한 일
- Session 방식과 JWT 방식의 차이 학습
- JWT 구조 (Header / Payload / Signature) 학습
- JWT 기반 Spring Security 프로젝트 구조 파악
- 클래스별 역할 분리 (AuthController / JwtAuthProvider / JwtAuthFilter / SecurityConfig) 학습
- 로그인 → JWT 발급 → Cookie 저장 → 재요청 시 검증 전체 흐름 학습

### 배운 점
- 세션 방식은 서버가 상태를 보유하는 Stateful 구조라 서버가 늘어나면 세션 공유 문제가 생기는 반면, JWT는 토큰 자체에 정보를 담아 서버가 상태를 보유하지 않는 Stateless 구조라 MSA나 다중 서버 환경에 적합함을 이해함
- JWT의 Payload는 복호화 가능하므로 비밀번호 같은 민감 정보를 담으면 안 되고, Signature가 위조 방지 역할을 한다는 보안 원리를 이해함
- `OncePerRequestFilter`를 사용해 요청마다 JWT를 검증하는 방식이 세션 없이 인증 상태를 유지하는 핵심 메커니즘임을 이해함
- `CustomUserDetailsService` → `JwtAuthProvider` → `JwtAuthFilter` → `SecurityConfig` 순서로 역할이 명확하게 분리되어 있어, 각 클래스가 단일 책임 원칙(SRP)을 따르는 구조임을 이해함
