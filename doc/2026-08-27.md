## 1. Jenkins 개요

코드 변경을 감지해 **빌드 → 테스트 → 배포를 자동화**하는 오픈소스 CI/CD 도구

- Java 기반으로 동작하며 **직접 서버에 설치**해서 운영
- 방대한 플러그인 생태계(2,000개 이상)로 다양한 도구와 연동 가능
- GitHub, Docker, Kubernetes, Slack 등 대부분의 DevOps 도구 연동 지원
- 기업 환경에서 가장 많이 사용되는 CI/CD 도구

**Jenkins가 해결하는 문제**

```
기존 수동 배포
    개발 → 직접 빌드 → 직접 서버 접속 → 파일 복사 → 서버 재시작
    → 사람이 직접 할수록 실수 발생, 반복 작업, 시간 낭비

Jenkins 자동화
    개발 → git push → Jenkins가 나머지 전부 처리
```

## 2. Jenkins 동작 원리

### 1) 트리거 방식

Jenkins는 코드 변경을 감지하는 방법이 두 가지다.

| 방식 | 설명 | 특징 |
|------|------|------|
| **Webhook** | GitHub가 push 이벤트 발생 시 Jenkins에 즉시 알림 | 실시간, 권장 방식 |
| **Polling** | Jenkins가 주기적으로 GitHub를 확인 | 딜레이 있음, 서버 부하 |

```
[Webhook 방식]
git push → GitHub → Webhook 발송 → Jenkins 트리거 → Pipeline 실행

[Polling 방식]
Jenkins → 주기적으로 GitHub 확인 → 변경 감지 → Pipeline 실행
```

### 2) Jenkins 내부 처리 구조

```
Jenkins Master (관리·조율)
    │
    ├── Job/Pipeline 스케줄링
    ├── 빌드 이력 관리
    ├── 플러그인 관리
    └── 웹 UI 제공
    │
    ▼
Jenkins Agent (실제 작업 실행)
    │
    ├── 코드 체크아웃
    ├── 빌드 실행
    ├── 테스트 실행
    └── 배포 실행
```

> 소규모 환경에서는 Master가 Agent 역할을 겸하는 단일 서버로 운영하기도 한다.

## 3. 전체 CI/CD 흐름

```
개발자
    │  git push (main / develop)
    ▼
GitHub Repository
    │  Webhook 전송
    ▼
Jenkins
    │
    ├── ① 소스 코드 체크아웃 (git clone)
    │
    ├── ② 빌드 (Gradle / Maven)
    │         ./gradlew clean build -x test
    │
    ├── ③ 테스트 실행
    │         단위 테스트, 통합 테스트
    │
    ├── ④ 코드 품질 검사 (SonarQube 연동 시)
    │
    ├── ⑤ Docker 이미지 빌드
    │         docker build -t 계정/app:latest .
    │
    ├── ⑥ Docker Hub Push
    │         docker push 계정/app:latest
    │
    └── ⑦ 운영 서버 배포
              SSH 접속 → docker-compose pull & up
    │
    ▼
Slack / Email 알림 (성공 / 실패)
    │
    ▼
배포 완료
```

## 4. Pipeline - Jenkinsfile

Jenkins의 CI/CD 작업 흐름을 코드로 정의하는 파일 (프로젝트 루트에 위치)

### 1) Declarative Pipeline (권장 방식)

```groovy
pipeline {
    agent any   // 사용 가능한 Agent에서 실행

    environment {
        DOCKER_HUB = credentials('docker-hub-credentials')  // Jenkins에 등록한 credentials 사용
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/계정/프로젝트.git'
            }
        }

        stage('Build') {
            steps {
                sh 'chmod +x ./gradlew'
                sh './gradlew clean build -x test'
            }
        }

        stage('Test') {
            steps {
                sh './gradlew test'
            }
            post {
                always {
                    junit 'build/test-results/**/*.xml'  // 테스트 결과 리포트
                }
            }
        }

        stage('Docker Build & Push') {
            steps {
                sh 'docker build -t 계정/app:latest .'
                sh 'docker push 계정/app:latest'
            }
        }

        stage('Deploy') {
            steps {
                sshagent(['server-ssh-key']) {
                    sh '''
                        ssh ubuntu@서버IP "
                            cd ~/app &&
                            docker-compose pull &&
                            docker-compose up -d
                        "
                    '''
                }
            }
        }
    }

    post {
        success { slackSend message: 'O 배포 성공' }
        failure { slackSend message: 'X 배포 실패 - 확인 필요' }
    }
}
```

### 2) Pipeline 구성 요소

| 구성 요소 | 설명 |
|---------|------|
| `pipeline` | 전체 파이프라인 블록 |
| `agent` | 실행할 Jenkins Agent 지정 (`any` = 사용 가능한 곳 어디서든) |
| `environment` | 환경변수 / credentials 정의 |
| `stages` | 전체 단계 묶음 |
| `stage` | 개별 단계 (Checkout, Build, Test, Deploy 등) |
| `steps` | 각 stage 안의 실제 실행 명령 |
| `post` | 성공/실패/항상 실행할 후처리 |

## 5. 주요 개념 및 용어

### 1) Credentials (자격 증명)

민감 정보(비밀번호, SSH 키, API 토큰)를 안전하게 관리하는 Jenkins 기능

```
Jenkins 관리 → Credentials → 등록
→ Jenkinsfile에서 credentials('등록한 ID')로 참조
```

- GitHub Actions의 `Secrets`와 동일한 역할
- 코드에 비밀번호를 직접 작성하지 않음

### 2) 브랜치 전략과 Pipeline 연동

| 브랜치 | 용도 | Pipeline 동작 |
|--------|------|-------------|
| `feature/*` | 기능 개발 | 빌드 + 테스트만 |
| `develop` | 통합 개발 | 빌드 + 테스트 + 개발 서버 배포 |
| `main` | 운영 배포 | 빌드 + 테스트 + 운영 서버 배포 |

### 3) Blue Ocean

Jenkins의 모던 UI 플러그인으로 Pipeline 시각화, 실행 상태를 직관적으로 확인 가능

### 4) 빌드 번호와 아티팩트

```
빌드 번호 : Jenkins가 자동 부여 (#1, #2, #3...)
아티팩트  : 빌드 결과물 (.jar, .war, Docker 이미지 등)
           → 빌드 번호별로 보관 → 롤백 시 이전 버전으로 재배포 가능
```

## 6. GitHub Actions vs Jenkins

| 구분 | GitHub Actions | Jenkins |
|------|---------------|---------|
| 설치 위치 | GitHub 클라우드 | 직접 서버에 설치 |
| 설정 파일 | `.yml` (YAML) | `Jenkinsfile` (Groovy) |
| 비용 | 무료 (월 한도 초과 시 유료) | 서버 운영 비용만 |
| 관리 부담 | 없음 | 서버·플러그인 직접 관리 |
| 커스터마이징 | 제한적 | 매우 자유로움 |
| 플러그인 | Actions Marketplace | 2,000개 이상 |
| 보안 민감 정보 | GitHub Secrets | Jenkins Credentials |
| 빌드 이력 관리 | GitHub UI | Jenkins 자체 대시보드 |
| 적합한 규모 | 소~중규모 | 중~대규모 / 기업 환경 |

**선택 기준**

```
소규모 프로젝트 / GitHub 중심 / 빠른 셋업
    └── GitHub Actions

대규모 / 기업 환경 / 세밀한 제어 / 다양한 도구 연동 / 오프라인 환경
    └── Jenkins
```

## 7. Jenkins 실무 활용 패턴

### 1) 롤백 (Rollback)

```
배포 실패 감지
    │
    ▼
이전 빌드 번호의 Docker 이미지로 재배포
    docker pull 계정/app:이전버전
    docker-compose up -d
```

### 2) 멀티 브랜치 Pipeline

```
develop push → 개발 서버 자동 배포
main push    → 운영 서버 자동 배포 (승인 단계 포함 가능)
```

### 3) 승인 단계 (Approval Gate)

```groovy
stage('Deploy to Production') {
    input {
        message "운영 서버에 배포하시겠습니까?"
        ok "배포 진행"
    }
    steps {
        // 운영 배포 실행
    }
}
```

운영 배포 전 담당자 승인을 받는 단계를 추가해 **실수로 인한 운영 배포를 방지**

### 4) 알림 연동

```groovy
post {
    success { slackSend color: 'good',    message: "O ${env.JOB_NAME} #${env.BUILD_NUMBER} 배포 성공" }
    failure { slackSend color: 'danger',  message: "X ${env.JOB_NAME} #${env.BUILD_NUMBER} 배포 실패" }
}
```

### 배운 점
- Jenkins는 서버를 직접 운영하는 만큼 관리 부담이 있지만 그만큼 파이프라인을 세밀하게 제어할 수 있어, 다양한 도구 연동과 복잡한 배포 전략이 필요한 기업 환경에서 선호됨을 이해함
- Jenkinsfile을 코드로 관리(IaC, Infrastructure as Code 개념)하면 배포 파이프라인 자체를 git으로 버전 관리할 수 있다는 점이 유용함을 이해함
- 운영 서버 배포 전 승인 단계(Approval Gate)를 추가하면 자동화의 편의성을 유지하면서도 실수로 인한 운영 배포 사고를 방지할 수 있음을 이해함
- Credentials로 민감 정보를 코드 외부에서 관리하는 방식이 GitHub Actions의 Secrets와 같은 개념임을 이해하면서 두 도구의 접근 방식이 유사함을 이해함
