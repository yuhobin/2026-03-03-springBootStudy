## 1. Spring Security 개요

Spring 애플리케이션의 **인증(Authentication)** 과 **인가(Authorization)** 를 담당하는 보안 프레임워크

모든 요청은 DispatcherServlet에 도달하기 전에 **Security 필터 체인을 먼저 통과**한다.

```
클라이언트 요청
        │
        ▼
Security Filter Chain     ← 인증 / 인가 검사
        │
        ├── 통과 → DispatcherServlet → Controller
        └── 거부 → 401 (인증 없음) / 403 (권한 없음)
```

## 2. 인증과 인가

| 구분 | 설명 | 예시 |
|------|------|------|
| **인증 (Authentication)** | 사용자가 누구인지 확인 | 로그인 |
| **인가 (Authorization)** | 인증된 사용자의 접근 권한 확인 | 관리자 페이지, 마이페이지 접근 |

**역할(Role) 분류 예시**

| 역할 | 대상 | 접근 가능 범위 |
|------|------|-------------|
| 게스트 | 비로그인 사용자 | 공개 페이지만 |
| `ROLE_USER` | 일반 로그인 회원 | 마이페이지, 댓글 작성 등 |
| `ROLE_ADMIN` | 관리자 | 전체 + 관리자 페이지 |

## 3. 인증 처리 흐름

로그인 요청이 들어왔을 때 Security 내부에서 처리되는 순서

```
사용자 로그인 요청 (id / pw 입력)
        │
        ▼
1. Authentication Filter       ← 요청을 가로채 인증 처리 위임
        │
        ▼
2. Authentication Manager      ← 어떤 방법으로 인증할지 결정
        │
        ▼
3. Authentication Provider     ← 실제 인증 수행
        │
        ├── 4. UserDetailsService  ← DB에서 사용자 정보 조회
        │         │
        │         └── UserDetails 반환 (id, pw, roles)
        │
        └── 5. PasswordEncoder    ← 입력 pw와 DB 암호화 pw 비교
                  │
                  ├── 일치 → 인증 성공 → SecurityContext(Session)에 저장
                  └── 불일치 → 인증 실패 → 실패 핸들러 실행
```

**구성 요소별 역할**

| 구성 요소 | 역할 |
|---------|------|
| `Authentication Filter` | 요청을 가로채 인증 처리를 위임 |
| `Authentication Manager` | 인증 방법 결정 (어떤 Provider 사용할지) |
| `Authentication Provider` | 실제 인증 수행 (DB 연동) |
| `UserDetailsService` | DB에서 사용자 정보 조회 → `UserDetails` 반환 |
| `PasswordEncoder` | 입력 비밀번호와 DB 암호화 값 비교 (BCrypt) |
| `SecurityContext` | 인증 성공 후 사용자 정보를 저장하는 공간 (Session 기반) |

## 4. 인터셉터와 Security 필터 비교

Spring MVC에는 인터셉터(`HandlerInterceptor`)도 있는데, Security 필터와 동작 위치가 다르다.

```
클라이언트 요청
        │
        ▼
Security Filter           ← DispatcherServlet 진입 전 처리
        │
        ▼
DispatcherServlet
        │
        ▼
Interceptor (preHandle)   ← Controller 실행 전
        │
        ▼
Controller 실행
        │
        ▼
Interceptor (postHandle)  ← Controller 실행 후, View 렌더링 전
        │
        ▼
ViewResolver → JSP
```

| 구분 | Security Filter | Interceptor |
|------|----------------|------------|
| 동작 위치 | DispatcherServlet 앞 | DispatcherServlet 내부 |
| 주요 용도 | 인증 / 인가 | 로깅, 세션 확인, 공통 처리 |
| 설정 방식 | SecurityConfig | `implements HandlerInterceptor` |

## 5. URL 권한 설정

접근 권한을 URL 패턴으로 지정한다. **위에서부터 순서대로 매칭**되므로 구체적인 패턴을 먼저 작성해야 한다.

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/admin/**").hasRole("ROLE_ADMIN")   // 관리자만
    .requestMatchers("/mypage/**").hasRole("ROLE_USER")   // 로그인 회원만
    .requestMatchers("/board/write").authenticated()       // 로그인한 사용자
    .requestMatchers("/login", "/member/**", "/board/**").permitAll()  // 누구나
    .anyRequest().authenticated()                          // 나머지는 로그인 필요
);
```

**주요 접근 표현식**

| 표현식 | 의미 |
|--------|------|
| `permitAll()` | 비로그인 포함 누구나 접근 가능 |
| `authenticated()` | 로그인한 사용자만 접근 가능 |
| `hasRole("ROLE_ADMIN")` | 특정 권한 보유자만 접근 가능 |
| `hasAnyRole(...)` | 여러 권한 중 하나 이상 보유 시 접근 가능 |

## 6. 세션 vs JWT

인증 성공 후 사용자 정보를 어디에 저장하느냐에 따라 방식이 나뉜다.

| 구분 | Session | JWT |
|------|---------|-----|
| 저장 위치 | 서버 메모리 | 클라이언트 (Cookie / Header) |
| 서버 종료 시 | 인증 정보 소멸 | 토큰 유효 시간까지 유지 |
| 확장성 | 서버 증가 시 세션 공유 필요 | 무상태(Stateless) → 확장 용이 |
| 보안 | 서버에서 관리 | 토큰 탈취 주의 |
| 주요 사용처 | 일반 웹 서비스 | REST API, 모바일 앱 |

> 현재는 Session 기반으로 학습하고, 이후 **JWT**로 확장할 예정

## 7. CSRF 방어

**CSRF(Cross Site Request Forgery)** : 인증된 사용자의 쿠키·세션을 탈취해 위조 요청을 보내는 공격

```java
// 개발 환경 : CSRF 비활성화 (간편하게 개발)
http.csrf(csrf -> csrf.disable())

// 운영 환경 : CSRF 활성화 권장 (기본값)
// → form 요청에 CSRF 토큰 자동 포함
```

> REST API(JWT) 방식에서는 쿠키를 사용하지 않으므로 CSRF 비활성화해도 무방하다.  
> 세션 기반 웹 서비스에서는 활성화 유지가 원칙이다.

- 세션 방식은 서버가 종료되면 인증 정보가 사라지는 한계가 있어 이를 보완하는 방식이 JWT이며, 이후 JWT 학습으로 이어진다는 흐름을 이해함
