## 1. JPA 쿼리 방식 비교

| 구분 | 메서드 규칙 | JPQL (`@Query`) | QueryDSL |
|------|-----------|----------------|---------|
| SQL 작성 | 메서드명으로 자동 생성 | 문자열로 직접 작성 | 코드로 작성 |
| 타입 안정성 | ❌ | ❌ (문자열 기반) | ✅ |
| 동적 쿼리 | ❌ 불가 | 어려움 | ✅ |
| 오타 감지 | 컴파일 시 | 런타임 시 | 컴파일 시 |
| 복잡한 조인/페이징 | ❌ | 가능 | ✅ 최적 |
| 초기 설정 난이도 | 낮음 | 낮음 | 높음 (Q-class 생성) |
| 주요 사용처 | 단순 조회 | 수정 / 삭제 / 정적 쿼리 | 복잡한 검색 / 필터링 |

**실무 사용 비율** : MyBatis 80% : JPA 20%  
→ 동적 쿼리가 많은 환경에서는 MyBatis가 유리, 단순 CRUD 중심은 JPA

## 2. 메서드 규칙 (JPQL 자동 생성)

Repository 인터페이스에 메서드명만 선언하면 JPA가 SQL을 자동 생성한다.

### 1) 기본 조회

```java
Emp findByEmpno(int empno);
// WHERE empno = ?

List<Emp> findByEname(String ename);
// WHERE ename = ?
```

### 2) LIKE

```java
List<Emp> findByEnameStartsWith(String ename);   // LIKE '?%'
List<Emp> findByEnameEndsWith(String ename);     // LIKE '%?'
List<Emp> findByEnameContains(String ename);     // LIKE '%?%'
```

### 3) 비교 연산자

```java
List<Emp> findBySalGreaterThan(int sal);         // sal > ?
List<Emp> findBySalGreaterThanEqual(int sal);    // sal >= ?
List<Emp> findBySalLessThan(int sal);            // sal < ?
List<Emp> findBySalLessThanEqual(int sal);       // sal <= ?
List<Emp> findBySalBetween(int min, int max);    // sal BETWEEN ? AND ?
```

### 4) AND / OR

```java
List<Emp> findByJobAndSalGreaterThan(String job, int sal);
// WHERE job = ? AND sal > ?

List<Emp> findByJobOrEname(String job, String ename);
// WHERE job = ? OR ename = ?
```

### 5) 정렬 / Top-N / 중복 제거

```java
List<Emp> findByOrderBySalDesc();
// ORDER BY sal DESC

List<Emp> findTop3ByOrderBySalDesc();
// 상위 3건만 (ROWNUM <= 3)

List<Emp> findDistinctByJob(String job);
// SELECT DISTINCT
```

### 6) NULL / NOT NULL / IN / NOT

```java
List<Emp> findByCommIsNull();             // WHERE comm IS NULL
List<Emp> findByCommIsNotNull();          // WHERE comm IS NOT NULL

List<Emp> findByDeptDeptnoIn(List<Integer> deptnos);
// WHERE deptno IN (10, 20, 30)

List<Emp> findByJobNot(String job);       // WHERE NOT job = ?
```

### 7) 연관 엔티티 조건 (JOIN)

```java
// Emp 엔티티가 Dept를 참조할 때, Dept의 컬럼으로 검색
List<Emp> findByDeptDname(String dname);
// JOIN dept WHERE dept.dname = ?

List<Emp> findByDeptDnameContains(String dname);
// JOIN dept WHERE dept.dname LIKE '%?%'
```

### 8) 메서드 규칙 키워드 요약

| 키워드 | SQL 변환 |
|--------|---------|
| `findBy컬럼명` | `WHERE 컬럼명 = ?` |
| `Contains` | `LIKE '%?%'` |
| `StartsWith` | `LIKE '?%'` |
| `EndsWith` | `LIKE '%?'` |
| `GreaterThan(Equal)` | `> (>=)` |
| `LessThan(Equal)` | `< (<=)` |
| `Between` | `BETWEEN ? AND ?` |
| `And` / `Or` | `AND` / `OR` |
| `OrderBy컬럼Desc/Asc` | `ORDER BY 컬럼 DESC/ASC` |
| `Top숫자` | 상위 N건 |
| `Distinct` | `SELECT DISTINCT` |
| `IsNull` / `IsNotNull` | `IS NULL` / `IS NOT NULL` |
| `Not` | `NOT` |
| `In` | `IN (...)` |

> **단점** : 조건이 많아질수록 메서드명이 길어짐  
> `findBySalGreaterThanAndEnameLikeAndJobLikeOrderByHiredateDesc` 처럼 가독성이 떨어질 수 있어, 복잡한 쿼리는 JPQL 또는 QueryDSL로 대체한다.

## 3. JPQL - @Query

JPA가 제공하는 **객체 중심의 쿼리 언어**로, 테이블명 대신 **Entity 클래스명**을 사용한다.  
`@Query` 어노테이션으로 직접 작성하며, 메서드 규칙으로 표현하기 어려운 쿼리에 사용한다.

**SQL vs JPQL 차이**

```sql
-- SQL : 테이블 기준
SELECT * FROM emp WHERE comm IS NULL

-- JPQL : Entity 객체 기준
SELECT e FROM Emp e WHERE e.comm IS NULL
```

### 1) 기본 사용법

```java
@Query("SELECT e FROM Emp e WHERE e.comm IS NULL")
List<Emp> findByCommIsNull();

@Query("SELECT e FROM Emp e WHERE e.job != :job")
List<Emp> findByJobNot(@Param("job") String job);
```

### 2) JOIN

```java
@Query("SELECT e FROM Emp e JOIN e.dept d WHERE d.deptno IN :deptnos")
List<Emp> findByDeptDeptnoIn(@Param("deptnos") List<Integer> deptnos);
// SQL의 테이블 JOIN 대신 Entity의 참조 필드(e.dept)를 기준으로 JOIN
```

- `:파라미터명` → `@Param("파라미터명")` 으로 바인딩
- SQL과 달리 Entity 필드명(`e.dept`)으로 JOIN → 테이블 구조보다 **객체 관계 기준**

### 3) JPQL 주요 특징

| 항목 | 내용 |
|------|------|
| 기준 | 테이블 X → Entity 클래스와 필드명 기준 |
| 파라미터 바인딩 | `:변수명` + `@Param` |
| 오타 감지 | 런타임 시 발견 (컴파일 시 감지 불가) |
| 동적 쿼리 | 어려움 → QueryDSL 사용 권장 |

## 4. QueryDSL

**타입 안정성**을 갖춘 코드 기반 쿼리 작성 방식  
복잡한 조인·필터링·페이징·동적 쿼리에 적합하다.

- 컴파일 시 오류 감지 → 런타임 에러 없음
- 동적 쿼리 작성 가능 (조건을 코드로 조합)
- 초기 설정이 복잡하고 **Q-class**를 별도 생성해야 함
- QueryDSL 전용 문법 학습이 필요

> 단순 조회는 메서드 규칙으로 충분하므로 QueryDSL은 **복잡한 검색·필터링·페이징**에서 진가를 발휘한다.

## 5. 상황별 선택 기준

```
단순 조회 (단일 컬럼 조건)
    └── 메서드 규칙

수정 / 삭제 / 복잡하지 않은 정적 쿼리
    └── JPQL (@Query)

복잡한 동적 쿼리 / 다중 조인 / 페이징
    └── QueryDSL 또는 MyBatis
```

### 배운 점
- 메서드 규칙은 단순하고 가독성이 좋지만 조건이 많아지면 메서드명이 길어져 오히려 가독성이 떨어진다는 한계를 이해함
- JPQL은 SQL과 거의 유사하지만 테이블명 대신 Entity 클래스명을 쓴다는 점이 핵심 차이로, JOIN 시 테이블 관계가 아닌 Entity의 참조 필드 기준으로 작성한다는 것을 이해함
- 메서드 규칙 → JPQL → QueryDSL 순으로 쿼리 복잡도에 따라 도구를 선택하는 기준이 명확해짐
