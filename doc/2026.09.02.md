## 1. 전체 배포 구조

```
로컬 개발 환경
    │  git push (main)
    ▼
GitHub Actions (ubuntu-latest 임시 환경)
    │  ① 코드 체크아웃
    │  ② JDK 21 세팅
    │  ③ Gradle 빌드 (.jar 생성)
    │  ④ Docker 이미지 빌드
    │  ⑤ Docker Hub에 push
    ▼
Docker Hub (이미지 저장소)
    │  ⑥ SSH로 AWS EC2 접속
    │  ⑦ .env 환경변수 파일 생성
    │  ⑧ docker-compose.yml 전송 (SCP)
    │  ⑨ docker-compose pull & up
    ▼
AWS EC2 (실제 운영 서버)
    │  컨테이너 실행
    ▼
서비스 운영
```

> GitHub Actions의 `ubuntu-latest`는 AWS EC2가 아닌 **GitHub이 임시 제공하는 Ubuntu 환경**이다.  
> 실제 서버(AWS EC2)는 SSH를 통해 원격으로 명령을 실행해 배포한다.

## 2. 사전 준비 - GitHub Secrets 등록

민감 정보는 코드에 직접 작성하지 않고 **GitHub Secrets**에 등록해서 `${{ secrets.키명 }}`으로 참조한다.

```
GitHub Repository → Settings → Secrets and variables → Actions → New repository secret
```

| Secret 키 | 내용 |
|-----------|------|
| `DOCKER_USERNAME` | Docker Hub 사용자명 |
| `DOCKER_PASSWORD` | Docker Hub 비밀번호 |
| `SERVER_SSH_KEY` | AWS EC2 SSH 개인키 (id_ed25519) |
| `DB_URL` | 데이터베이스 연결 URL |
| `DB_USERNAME` | DB 사용자명 |
| `DB_PASSWORD` | DB 비밀번호 |

> SSH 키는 AWS EC2 생성 시 발급받은 `.pem` 또는 `id_ed25519` 개인키를 그대로 붙여넣는다.

## 3. deploy.yml 전체 흐름

```yaml
name: Deploy With Docker to AWS Server

on:
  push:
    branches:
      - main          # main 브랜치에 push될 때 자동 실행

jobs:
  deploy:
    runs-on: ubuntu-latest   # GitHub 제공 임시 Ubuntu 환경
    steps:
      - Checkout repository
      - SetUp JDK 21
      - Set gradlew permission
      - Build with Gradlew
      - Login DockerHub
      - Build Docker Image
      - Push Docker Image
      - Set SSH key Permission
      - Add SSH Key
      - Add Known_hosts
      - 환경설정 (.env 파일 생성)
      - SCP docker-compose.yml 전송
      - DockerHub Image pull & 컨테이너 실행
```

## 4. 단계별 상세 설명

### 1) 코드 체크아웃 & JDK 설정

```yaml
- name: Checkout repository
  uses: actions/checkout@v4

- name: SetUp JDK 21
  uses: actions/setup-java@v4
  with:
    distribution: 'temurin'   # Eclipse Temurin JDK (가장 최소 단위)
    java-version: '21'
```

### 2) Gradle 빌드

```yaml
- name: Set gradlew permission
  run: chmod +x ./gradlew     # 실행 권한 부여

- name: Build with Gradlew
  run: ./gradlew clean build -x test  # 테스트 생략하고 빌드
```

### 3) Docker 이미지 빌드 & Hub 업로드

```yaml
- name: Login DockerHub
  run: |
    echo "${{ secrets.DOCKER_PASSWORD }}" | \
    docker login -u "${{ secrets.DOCKER_USERNAME }}" --password-stdin

- name: Build Docker Image
  run: docker build -t ${{ secrets.DOCKER_USERNAME }}/last-app:latest .

- name: Push Docker Image
  run: docker push ${{ secrets.DOCKER_USERNAME }}/last-app:latest
```

### 4) AWS EC2 SSH 연결

```yaml
# SSH 개인키 파일 생성 및 권한 설정
- name: Set SSH key Permission
  run: |
    mkdir -p ~/.ssh
    echo "${{ secrets.SERVER_SSH_KEY }}" > ~/.ssh/id_ed25519
    chmod 600 ~/.ssh/id_ed25519   # 소유자만 읽기 가능 (SSH 보안 요구사항)

# SSH 에이전트에 키 등록
- name: Add SSH Key
  uses: webfactory/ssh-agent@v0.5.3
  with:
    ssh-private-key: ${{ secrets.SERVER_SSH_KEY }}

# 서버 호스트 키 등록 (최초 접속 시 known_hosts 확인 우회)
- name: Add Known_hosts
  run: ssh-keyscan -H 13.124.133.9 >> ~/.ssh/known_hosts
```

### 5) DB 환경변수 파일 생성 (.env)

```yaml
- name: 환경설정
  run: |
    ssh ubuntu@13.124.133.9 << EOF
      mkdir -p ~/app && cd ~/app
      rm -f .env
      echo "DB_URL=${{ secrets.DB_URL }}"           >> ~/app/.env
      echo "DB_USERNAME=${{ secrets.DB_USERNAME }}" >> ~/app/.env
      echo "DB_PASSWORD=${{ secrets.DB_PASSWORD }}" >> ~/app/.env
      chmod 600 ~/app/.env   # 소유자만 읽기 가능
    EOF
```

- DB 연결 정보를 `.env` 파일로 EC2에 직접 생성
- `docker-compose.yml`에서 `env_file: .env`로 참조

### 6) 배포 실행

```yaml
# docker-compose.yml을 SCP로 EC2에 전송
- name: SCP docker-compose
  run: |
    ssh ubuntu@13.124.133.9 "mkdir -p /home/ubuntu/app"
    scp docker-compose.yml ubuntu@13.124.133.9:/home/ubuntu/app/docker-compose.yml

# 컨테이너 재시작
- name: DockerHub Image using
  run: |
    ssh ubuntu@13.124.133.9 << 'EOF'
      cd /home/ubuntu/app
      docker-compose down          # 기존 컨테이너 종료
      docker-compose pull          # 최신 이미지 다운로드
      docker-compose up -d         # 백그라운드로 컨테이너 실행
    EOF
```

## 5. docker-compose.yml

EC2 서버에서 컨테이너를 어떻게 실행할지 정의하는 파일 (SCP로 EC2에 전송됨)

```yaml
version: "3"
services:
  app:
    image: 도커허브계정/last-app:latest
    ports:
      - "8080:8080"
    env_file:
      - .env          # DB 정보를 .env 파일에서 로드
    restart: always   # 컨테이너 다운 시 자동 재시작
```

## 6. Jenkins - 대안 CI/CD 도구

GitHub Actions 외에 **Jenkins**를 사용한 CI/CD 방식도 있다.

**Jenkins 동작 방식**

```
GitHub push
    │  Webhook 전송
    ▼
Jenkins 서버 (직접 운영)
    │  Pipeline 실행
    │  ① 코드 체크아웃
    │  ② 빌드
    │  ③ 테스트
    │  ④ Docker 빌드 & 배포
    ▼
운영 서버
```

**Jenkins 기본 구성**

```groovy
// Jenkinsfile (Pipeline 스크립트)
pipeline {
    agent any
    stages {
        stage('Checkout') {
            steps { git 'https://github.com/계정/프로젝트' }
        }
        stage('Build') {
            steps { sh './gradlew clean build -x test' }
        }
        stage('Docker Build & Push') {
            steps {
                sh 'docker build -t 계정/app:latest .'
                sh 'docker push 계정/app:latest'
            }
        }
        stage('Deploy') {
            steps {
                sh 'ssh ubuntu@서버IP "cd ~/app && docker-compose up -d"'
            }
        }
    }
}
```

## 7. GitHub Actions vs Jenkins 비교

| 구분 | GitHub Actions | Jenkins |
|------|---------------|---------|
| 서버 | GitHub 제공 (별도 서버 불필요) | 직접 운영 (서버 필요) |
| 설정 | YAML 파일 (.yml) | Groovy 스크립트 (Jenkinsfile) |
| 비용 | 무료 (월 한도) | 서버 운영 비용 |
| GitHub 연동 | 네이티브 통합 | Webhook 설정 필요 |
| 커스터마이징 | 제한적 | 자유도 높음 |
| 플러그인 | Actions Marketplace | 방대한 플러그인 생태계 |
| 적합한 규모 | 소~중규모 프로젝트 | 중~대규모 / 기업 환경 |

## 💡 Note

### 오늘 한 일
- GitHub Actions + Docker + AWS EC2 자동 배포 파이프라인 구성
- GitHub Secrets로 민감 정보(DB, Docker, SSH) 관리 학습
- SSH를 통한 원격 EC2 명령 실행 및 docker-compose 배포 학습
- `.env` 파일로 DB 환경변수를 분리해서 컨테이너에 주입하는 방법 학습
- Jenkins 기반 CI/CD 구조 학습 및 GitHub Actions와 비교

### 배운 점
- `ubuntu-latest`는 GitHub이 임시 제공하는 환경이고, 실제 운영 서버(AWS EC2)는 SSH로 원격 접속해서 명령을 실행하는 구조임을 이해함
- 민감 정보(DB 연결, SSH 키, Docker 비밀번호)는 절대 코드에 직접 작성하지 않고 GitHub Secrets에 등록해 `${{ secrets.키명 }}`으로 참조하는 것이 보안 원칙임을 이해함
- `chmod 600`은 SSH 키와 `.env`처럼 중요 파일에 소유자만 읽기 권한을 부여하는 리눅스 권한 설정으로, SSH 연결 시 보안 요구사항임을 이해함
- Jenkins는 GitHub Actions보다 자유도가 높고 기업 환경에서 많이 쓰이며, 직접 서버를 운영하므로 세밀한 파이프라인 제어가 가능하다는 차이를 이해함
