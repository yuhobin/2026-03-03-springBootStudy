## 1. 인증 방식 개요

로그인한 사용자를 **다음 요청에서도 식별**하기 위해 인증 상태를 유지하는 방법이 필요하다.  
HTTP는 기본적으로 무상태(Stateless) 프로토콜이므로, 요청마다 사용자를 식별하는 별도 메커니즘이 필요하다.

대표적인 두 가지 방식이 **Session**과 **JWT**다.

---

## 2. Session 인증

**서버가 인증 상태를 직접 보관**하는 방식 (Stateful)

### 1) 동작 흐름

```
로그인 요청 (id / pwd)
        │
        ▼
서버 : ID/PW 확인 (DB 조회)
        │
        ▼
Session 생성 → 서버 메모리에 저장
        │  세션 ID 발급
        ▼
클라이언트 : JSESSIONID 쿠키 저장
        │
        ▼
다음 요청 시 JSESSIONID 쿠키 자동 전송
        │
        ▼
서버 : Session 저장소에서 세션 ID 확인 → 사용자 식별
        │
        ▼
요청 처리
```

### 2) Spring Security Session 처리

```java
// Spring Security가 자동으로 처리
// 개발자는 SecurityConfig에서 정책만 설정
http.sessionManagement(session -> session
    .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
);

// Controller에서 로그인 사용자 접근
@GetMapping("/mypage")
public String mypage(HttpSession session) {
    String userid = (String) session.getAttribute("userid");
}
```

## 3. JWT 인증

**클라이언트가 인증 정보를 직접 보관**하는 방식 (Stateless)

### 1) JWT 구조

```
Header . Payload . Signature
  │          │          │
알고리즘   실제 데이터   위조 방지 서명
           (id, role,
           만료시간)
```

> Payload는 Base64 인코딩으로 **누구나 디코딩 가능**  
> → 비밀번호 등 민감 정보는 절대 담지 않는다  
> → 위조 방지는 Signature가 담당 (비밀키로 서명)

### 2) 동작 흐름

```
로그인 요청 (id / pwd)
        │
        ▼
서버 : ID/PW 확인 (DB 조회)
        │  AuthenticationManager → UserDetailsService → DB
        ▼
JwtProvider : JWT 토큰 생성
        │  Payload에 username, role, 만료시간 포함
        ▼
클라이언트 : JWT 저장 (Cookie 또는 LocalStorage)
        │
        ▼
다음 요청 시 JWT 전송
        │  Cookie 자동 전송 또는 Authorization: Bearer JWT
        ▼
JwtAuthenticationFilter (OncePerRequestFilter)
        │  ① JWT 추출
        │  ② 서명 검증 (위조 여부)
        │  ③ 만료 여부 확인
        │  ④ username 추출 → DB 조회
        │  ⑤ SecurityContext에 인증 정보 저장
        ▼
요청 처리 (Controller 접근)
```

### 3) Spring Security JWT 처리

```java
// Session을 사용하지 않도록 설정
http.sessionManagement(session -> session
    .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
);

// JwtAuthenticationFilter를 Security 필터 체인에 추가
http.addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
```

## 4. 핵심 차이 비교

| 구분 | Session | JWT |
|------|---------|-----|
| **인증 정보 저장** | 서버 메모리 | 클라이언트 (Cookie / Header) |
| **서버 상태** | Stateful | Stateless |
| **식별 방법** | 세션 ID로 서버 조회 | 토큰 자체를 서버에서 검증 |
| **전송 방식** | JSESSIONID 쿠키 자동 전송 | Cookie 또는 `Authorization: Bearer` 헤더 |
| **서버 종료 시** | 인증 정보 소멸 | 토큰 유효 기간까지 유지 |
| **수평 확장** | 세션 공유 필요 (Redis 등) | 서버 간 공유 불필요 |
| **강제 로그아웃** | 서버에서 세션 즉시 삭제 가능 | 토큰 만료 전까지 불가 (블랙리스트 필요) |
| **보안 위협** | CSRF 공격 주의 | 토큰 탈취 주의 (XSS 공격) |

## 5. 장단점 및 사용 상황

### 1) Session 방식

**장점**
- 서버에서 세션을 즉시 무효화할 수 있어 **강제 로그아웃·보안 제어 용이**
- 구현이 단순하고 Spring Security 기본 지원
- 민감한 정보가 서버에만 존재

**단점**
- 서버 메모리에 세션 저장 → 사용자 증가 시 **메모리 부담**
- 서버가 여러 대인 경우 세션 공유 문제 (별도 세션 저장소 필요)
- 서버 재시작 시 모든 로그인 상태 초기화

**적합한 상황**
- 일반적인 웹 서비스 (쇼핑몰, 커뮤니티, 관리자 페이지)
- 단일 서버 또는 소규모 서비스
- 즉각적인 권한 취소가 필요한 서비스 (금융, 보안 중요 서비스)

---

### 2) JWT 방식

**장점**
- 서버가 상태를 보유하지 않아 **수평 확장(Scale-out) 용이**
- 서버 간 세션 공유 불필요 → MSA, 분산 환경에 적합
- 모바일 앱, 다른 도메인 API 서버와 연동 용이

**단점**
- 토큰 탈취 시 만료 전까지 강제 무효화 어려움 (블랙리스트 관리 필요)
- Payload 노출 가능 → 민감 정보 포함 금지
- 토큰 크기가 커서 요청마다 데이터 전송량 증가

**적합한 상황**
- REST API 서버 (Vue, React 프론트엔드와 분리된 구조)
- MSA(마이크로서비스 아키텍처)
- 모바일 앱 인증
- 여러 서비스 간 인증 공유 (소셜 로그인 등)

---

### 3) 선택 기준 요약

```
단일 서버 / 즉각 권한 제어 필요 / 일반 웹
    └── Session

REST API / 모바일 / MSA / 다중 서버 / 프론트-백 분리
    └── JWT
```

## 6. BCryptPasswordEncoder

두 방식 모두 비밀번호는 반드시 **BCrypt로 암호화**해서 저장한다.

```java
@Bean
public BCryptPasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

// 회원가입 : 암호화해서 저장
String encoded = passwordEncoder.encode(rawPassword);

// 로그인 : 입력값과 DB 암호화 값 비교
boolean isMatch = passwordEncoder.matches(rawPassword, encodedPassword);
```

**BCrypt 특징**

| 특징 | 설명 |
|------|------|
| Salt 자동 적용 | 같은 비밀번호도 암호화할 때마다 다른 해시값 생성 |
| 단방향 암호화 | 복호화 불가 → DB 탈취 시 원문 확인 불가 |
| 자동 비교 | `matches()`로 입력값과 해시값을 자동 비교 |
| 다중 패턴 | 동일 비밀번호라도 여러 해시 패턴을 생성해 Rainbow Table 공격 방어 |

## 💡 Note

### 오늘 한 일
- Session / JWT 두 인증 방식의 동작 흐름 비교 학습
- 각 방식의 장단점과 적합한 사용 상황 파악
- Spring Security에서 두 방식을 각각 설정하는 방법 학습
- BCryptPasswordEncoder의 암호화 원리 학습

### 배운 점
- Session은 서버가 상태를 직접 관리하는 Stateful 방식이라 즉각적인 권한 제어가 가능하지만, 서버가 늘어날수록 세션 공유 문제가 생긴다는 한계를 이해함
- JWT는 토큰 자체에 인증 정보를 담아 서버가 상태를 보유하지 않는 Stateless 방식이라 MSA나 프론트-백 분리 구조에 적합하지만, 토큰 탈취 시 만료 전까지 강제 무효화가 어렵다는 단점을 이해함
- BCrypt는 같은 비밀번호라도 Salt로 인해 매번 다른 해시값을 생성하므로 Rainbow Table 공격을 방어할 수 있으며, Spring Security가 `matches()`로 자동 비교해주므로 복호화 없이 검증이 가능함을 이해함
- 현재 진행 중인 프로젝트처럼 Thymeleaf + Spring Boot 구조의 일반 웹 서비스는 Session이, Vue/React + REST API 분리 구조는 JWT가 더 자연스러운 선택임을 이해함
