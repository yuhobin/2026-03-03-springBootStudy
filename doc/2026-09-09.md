## 1. 프로젝트 개요

냉장고에 있는 재료를 선택하면 **Gemini API + pgVector 유사도 검색**으로 가장 적합한 레시피를 추천하는 Spring AI 기반 서비스

- 레시피 원본 데이터(Oracle) → 벡터값(PostgreSQL pgVector) 변환 후 저장
- 선택한 재료를 벡터로 변환 → Cosine Distance로 가장 가까운 레시피 검색
- Jenkins로 빌드 → Docker 이미지 생성 → AWS EC2 자동 배포

## 3. RAG 기반 레시피 추천 흐름

### 1) 사전 Vector 데이터 저장 (초기 1회)

```
Oracle : 레시피 원본 데이터
        │  레시피명 + 재료 + 조리법 → content 문자열 생성
        ▼
Chunk 분할 (일정 크기로 자르기 + Overlap으로 문맥 유지)
        │
        ▼
EmbeddingModel (Gemini API)
        │  String → float[] (벡터 변환)
        ▼
PostgreSQL recipe_vector 테이블 저장
        │  content + embedding(float[]) 저장
```

### 2) 실시간 레시피 추천

```
사용자 재료 선택 (닭고기, 감자, 양파)
        │  재료 목록 → 검색 문장 생성
        ▼
EmbeddingModel (Gemini API)
        │  검색 문장 → queryVector (float[])
        ▼
pgVector Cosine Distance 검색
        │  embedding <=> queryVector → 거리 계산
        │  거리가 작은 순(유사도 높은 순) → LIMIT 5
        ▼
유사 레시피 5개 반환
        │
        ▼
Thymeleaf 화면 출력 (레시피명 / 재료 / 조리법 / 충족률)
```

**Vector 유사도 검색 원리**

```
"닭고기, 감자, 양파" → [0.12, 0.87, 0.34, ...]
                              ↓ Cosine Distance 계산
레시피 A 벡터 : distance = 0.05  ← 가장 유사 (추천)
레시피 B 벡터 : distance = 0.31
레시피 C 벡터 : distance = 0.67  ← 거리 멀수록 비유사
```

> `distance` 값이 작을수록 입력 재료와 의미적으로 가까운 레시피

## 4. Vector DB 저장 과정

### 1) Chunk & Overlap

긴 레시피 텍스트를 그대로 벡터화하면 의미가 희석되므로 일정 크기로 분할한다.

```
전체 content (5,000자)
    ├── Chunk 0 : 0 ~ 999자
    ├── Chunk 1 : 800 ~ 1,799자    ← Overlap 200자 겹침
    ├── Chunk 2 : 1,600 ~ 2,566자
    └── ...
```

- **Chunk** : 문서를 일정 크기로 자름
- **Overlap** : 인접 청크가 일부 내용을 공유해 문맥 유지

### 2) PostgreSQL 저장 구조

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `recipe_id` | INT | Oracle 원본 레시피 ID (FK) |
| `content` | TEXT | 청크 텍스트 |
| `embedding` | vector | float[] 벡터 값 |

### 3) 핵심 원칙

```
저장 시 Embedding 모델 = 검색 시 Embedding 모델 (반드시 동일)
→ 모델마다 벡터 공간이 달라 다른 모델끼리는 거리 비교 불가
```

## 5. Jenkins CI/CD 파이프라인

### 1) 전체 파이프라인 흐름

```
git push (main)
        │  Webhook 트리거
        ▼
Jenkins Pipeline 시작
        │
        ├── Stage 1  : Repository Checkout
        ├── Stage 2  : .env 파일 생성 (Credentials 사용)
        ├── Stage 3  : Gradle 권한 설정 (chmod +x gradlew)
        ├── Stage 4  : Gradle Build (./gradlew clean build -x test)
        ├── Stage 5  : Docker Image 빌드
        ├── Stage 6  : Docker Hub 로그인
        ├── Stage 7  : Docker Hub Push
        ├── Stage 8  : docker-compose down (기존 컨테이너 종료)
        ├── Stage 9  : docker-compose pull (최신 이미지 다운)
        ├── Stage 10 : docker-compose up -d (컨테이너 실행)
        └── Stage 11 : 컨테이너 상태 확인 (docker compose ps)
        │
        ▼
post : 성공 / 실패 메시지 출력
```

### 2) 환경변수 설정

```groovy
environment {
    APP_DIR      = "~/app"
    JAR_NAME     = "SpringRecipeAIProject-0.0.1-SNAPSHOT.jar"
    DOCKER_IMAGE = "yuhobin/ai-app:latest"
}
```

## 6. Jenkinsfile 단계별 설명

### Stage 1 - Git Checkout

```groovy
stage("Repository Checkout") {
    steps {
        checkout scm  // Jenkins가 연결된 Git Repository 코드 체크아웃
    }               // scm = Git URL + Jenkinsfile 자동 인식
}
```

### Stage 2 - .env 파일 생성 (Credentials)

```groovy
stage("Create .env") {
    steps {
        withCredentials([
            string(credentialsId: 'post-url', variable: 'POST_URL'),
            string(credentialsId: 'gen-key',  variable: 'GEN_KEY')
        ]){
            sh '''
                echo "SPRING_PROFILES_ACTIVE=prod" > .env
                echo "POST_URL=${POST_URL}" >> .env   # PostgreSQL 연결 URL
                echo "GEN_KEY=${GEN_KEY}"  >> .env    # Gemini API Key
                chmod 600 .env                         # 소유자만 읽기 권한
            '''
        }
    }
}
```

- `withCredentials` : Jenkins Credentials에 등록한 민감 정보를 안전하게 주입
- `.env` 파일로 DB URL, Gemini API Key 등을 컨테이너에 전달
- `chmod 600` : 소유자만 읽기 가능 (보안 필수)

### Stage 3~4 - Gradle 빌드

```groovy
stage("Gradle Permission") {
    steps { sh 'chmod +x gradlew' }  // 실행 권한 부여
}

stage("Gradlew Build") {
    steps { sh './gradlew clean build -x test' }  // 테스트 생략, jar 생성
}
```

### Stage 5~7 - Docker 이미지 빌드 & Hub 업로드

```groovy
stage("Docker Build") {
    steps { sh 'docker build -t ${DOCKER_IMAGE} .' }
}

stage("DockerHub Login") {
    steps {
        withCredentials([usernamePassword(
            credentialsId: 'dockerhub_info',
            usernameVariable: 'DH_USER',
            passwordVariable: 'DH_PASS'
        )]){
            sh 'echo "$DH_PASS" | docker login -u "$DH_USER" --password-stdin'
        }
    }
}

stage("DockerHub Push") {
    steps { sh 'docker push ${DOCKER_IMAGE}' }
}
```

### Stage 8~11 - 배포 실행

```groovy
stage("Docker Compose DOWN") {
    steps { sh 'docker compose down || true' }  // 실패해도 계속 진행
}

stage("Docker Compose Pull") {
    steps { sh 'docker compose pull' }
}

stage("Docker Compose Up") {
    steps { sh 'docker compose up -d' }
}

stage("Container Check") {
    steps { sh 'docker compose ps' }  // 실행 상태 확인
}
```

### post - 성공 / 실패 처리

```groovy
post {
    success {
        echo 'Docker Compose 배포 성공'
    }
    failure {
        echo 'Docker Compose 배포 실패'
        sh 'docker compose ps || true'  // 실패 시 컨테이너 상태 출력
    }
}
```

- Oracle 레시피 데이터 → Chunk 분할 → Embedding → pgVector 저장 과정 구현
- 재료 선택 → Vector 유사도 검색 → 추천 레시피 출력 흐름 실습
- Jenkinsfile 11단계 파이프라인 작성 및 AWS EC2 자동 배포 실습

### 배운 점
- 재료 텍스트를 float[] 벡터로 변환해 Cosine Distance로 가장 가까운 레시피를 찾는 방식이 기존 LIKE 검색보다 의미적으로 훨씬 정확한 결과를 반환함을 이해함
- Jenkins Credentials의 `withCredentials`로 Gemini API Key, DB URL 같은 민감 정보를 코드에 노출하지 않고 안전하게 주입할 수 있다는 것을 이해함
- `docker compose down || true` 패턴은 기존 컨테이너가 없어 `down` 명령이 실패해도 파이프라인이 중단되지 않도록 하는 방어 코드임을 이해함
- `post { success / failure }` 블록으로 배포 성공/실패에 따른 후처리를 명확히 분리할 수 있고, 실패 시 `docker compose ps`로 컨테이너 상태를 즉시 확인할 수 있는 디버깅 패턴을 이해함
