## 1. RAG 개요

**RAG (Retrieval-Augmented Generation)**  
AI가 답변을 생성할 때 **사전에 저장해둔 데이터를 검색해서 참고**하는 방식

- 일반 AI : 학습된 데이터만으로 답변 생성 → 최신 정보 반영 불가
- RAG : DB에서 관련 데이터를 먼저 검색 → 검색 결과를 기반으로 답변 생성

```
[일반 AI]
사용자 질문 → AI 모델 → 답변 (학습 데이터만 활용)

[RAG]
사용자 질문 → Vector 검색 → 관련 데이터 추출 → AI 모델 → 정확한 답변
```

**Vector 검색 원리**

텍스트를 숫자 배열(벡터)로 변환해 의미적으로 가장 가까운 데이터를 찾는다.

```
"Java 기초 강좌" → EmbeddingModel → [0.12, 0.87, 0.34, ...]
                                              float[]
```

- 의미가 유사할수록 벡터 공간에서 **거리가 가까움**
- 거리가 가장 작은 값 순으로 정렬 → 유사 데이터 추천

## 2. 전체 구현 흐름

### 1) 사전 데이터 저장 (초기 1회)

```
Oracle DB (원본 데이터)
        │  강좌/맛집/상품 데이터 조회
        ▼
Content 문자열 생성 (최대 5,000자)
        │
        ▼
Chunk 분할 (1,000자 단위 + Overlap)
        │
        ▼
EmbeddingModel (Gemini API)
        │  String → float[] 변환
        ▼
PostgreSQL + pgVector 저장
        │  content + embedding 저장
```

### 2) 사용자 검색 시 (실시간)

```
사용자 입력 (검색어)
        │
        ▼
EmbeddingModel → queryVector (float[])
        │
        ▼
pgVector Cosine Distance 검색
        │  저장된 벡터와 거리 계산 → 가까운 순 정렬
        ▼
유사 데이터 추출 (Top N)
        │
        ▼
Gemini API → 최종 추천 결과 생성
```

## 3. Chunk & Overlap

긴 텍스트를 그대로 벡터로 변환하면 의미가 희석되므로, **일정 크기로 잘라서** 벡터화한다.

### 1) Chunk (청크)

```
전체 content (5,000자)
    │
    ├── Chunk 0 : 0 ~ 999자
    ├── Chunk 1 : 800 ~ 1,799자
    ├── Chunk 2 : 1,600 ~ 2,566자
    └── ...
```

### 2) Overlap (겹침)

인접한 청크끼리 **일부 내용을 겹치게** 만들어 문맥이 끊기지 않게 처리

```
Chunk 1 :  "Spring Boot에서는 Spring Security를 사용하여 사용자의 로그인과"
Chunk 2 :  "사용자의 로그인과 권한을 관리할 수 있습니다."
                    ↑
              겹치는 부분 (Overlap)
              → "사용자의 로그인과" 문맥이 이어짐
```

**Chunk / Overlap 핵심 요약**

| 개념 | 설명 |
|------|------|
| `Chunk` | 긴 문서를 일정 크기로 잘라 각각 벡터화 |
| `Overlap` | 인접 청크 간 일부 내용을 겹쳐 문맥 유지 |
| 필요한 이유 | AI Embedding 모델은 입력 길이 제한이 있고, 짧을수록 의미 정확도가 높음 |

### 3) StringBuffer vs StringBuilder

Chunk 처리 시 문자열 생성에 사용

| 구분 | StringBuffer | StringBuilder |
|------|-------------|--------------|
| 동기 방식 | ✅ (Thread-safe) | ❌ |
| 비동기 방식 | ❌ | ✅ |
| 속도 | 느림 | 빠름 |
| 사용 상황 | 멀티스레드 환경 | 단일스레드 (일반적인 Chunk 처리) |

## 4. Vector DB 저장 과정

### 1) Content 생성

Oracle DB의 원본 데이터를 하나의 텍스트로 변환

```java
// 강좌 데이터를 검색 가능한 문장으로 변환
String content = createCourseContent(course);
// "자바 기초 강좌 | 강사: 홍길동 | 레벨: 입문 | 내용: 객체지향 프로그래밍..."
```

### 2) Chunk 분할 후 Embedding 생성

```java
// Chunk 분할 (size: 1000, overlap: 200)
List<String> chunks = chunkText(content, 1000, 200);

for (String chunk : chunks) {
    // EmbeddingModel로 벡터 변환 (Gemini API 호출)
    float[] vector = embeddingModel.embed(chunk);

    // PostgreSQL에 저장
    CourseVectorVO vo = CourseVectorVO.builder()
        .courseId(course.getId())
        .content(chunk)
        .embedding(vector)
        .build();

    mapper.insertVector(vo);
}
```

### 3) PostgreSQL 저장 구조

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | SERIAL | 자동 증가 PK |
| `course_id` | INT | Oracle 원본 데이터 ID (FK) |
| `content` | TEXT | 청크 텍스트 |
| `embedding` | vector | float[] 벡터 값 |

## 5. 유사도 검색 및 추천

### 1) Cosine Distance 검색

```sql
-- pgVector : 입력 벡터와 가장 유사한 데이터 검색
SELECT course_id, content,
       embedding <=> #{queryVector} AS distance
FROM course_vector
ORDER BY distance ASC
LIMIT 5
```

- `<=>` : pgVector의 Cosine Distance 연산자
- `distance`가 작을수록 유사도 높음
- `LIMIT 5` : 가장 유사한 상위 5개 반환

### 2) Gemini API로 최종 답변 생성

검색된 유사 데이터를 Gemini에 전달해 자연스러운 추천 결과를 생성한다.

```java
// 검색된 content를 프롬프트에 포함
String prompt = """
    다음 강좌 정보를 바탕으로 사용자에게 추천해줘:
    %s
    사용자 요청: %s
    """.formatted(similarContents, userQuery);

String result = chatModel.call(prompt);  // Gemini API 호출
```

## 6. 기술 스택 구성

| 기술 | 역할 |
|------|------|
| **Spring AI** | EmbeddingModel / ChatModel 인터페이스 제공 |
| **Gemini API** | 텍스트 → 벡터 변환 (Embedding) / 최종 답변 생성 (Chat) |
| **PostgreSQL + pgVector** | 벡터 저장 및 Cosine Distance 유사도 검색 |
| **Oracle** | 원본 데이터 저장 (강좌, 맛집 등) |
| **MyBatis** | Oracle / PostgreSQL 쿼리 처리 |

**RAG 구현 핵심 원칙**

```
1. 저장 시 사용한 Embedding 모델 = 검색 시 사용하는 모델 (반드시 동일)
2. Chunk 크기가 너무 크면 의미 희석, 너무 작으면 문맥 손실
3. Overlap으로 Chunk 경계의 문맥 유실 방지
4. Cosine Distance가 작은 순 = 의미적으로 가장 유사한 데이터
```

### 배운 점
- RAG는 AI가 학습 데이터 외에 실시간으로 DB를 검색해서 답변을 생성하므로, 학습 데이터에 없는 최신·맞춤 정보도 정확하게 추천할 수 있다는 것을 이해함
- Chunk를 Overlap으로 겹치게 분할하는 이유는 "사용자의 로그인과"처럼 청크 경계에 걸친 문장의 문맥이 끊기지 않게 하기 위함임을 이해함
- 저장 시와 검색 시 반드시 동일한 Embedding 모델을 써야 하는 이유는, 모델마다 벡터 공간(차원 수, 방향)이 달라 다른 모델로 만든 벡터끼리는 거리 비교가 의미 없기 때문임을 이해함
- pgVector의 `<=>` 연산자로 Cosine Distance를 계산해 가장 가까운 값을 추천하는 것이 Vector 검색의 핵심 쿼리임을 이해함
